# 자원 배분 — 분리하지 않고 격리하기

> **상태: 7단계 전부 완료·배포 (2026-09-11).** 이 문서는 착수 전 판단 기록이고, 아래
> 표의 "오늘" 열은 그 시점의 상태다. 실제로 반영된 값과 달라진 결정은 이 블록에 적는다.
>
> - **전제가 바뀌었다**: §6 마지막 미결정("옆 스택에도 제한이 필요한가")은 odysseus 와
>   RAG Backborn 을 **2222 서버로 이전**해 해소됐다. 2224 는 memora 전용이므로 상한은
>   memora 만 양보하는 구조가 아니다. 그래서 §1 값도 전용 호스트 기준으로 키웠다.
> - **§1**: postgres 2.5/2560m · backend 3.0/3584m · worker 2.5/2048m · frontend 1.0/640m ·
>   seaweedfs 1.0/768m · nginx 0.5/128m (예약 합 3.8G). 메모리 상한 합 9.5G < 11.4G 는
>   의도 — 동시에 상한을 치면 호스트 OOM 이 되어 커널이 임의로 죽인다. Postgres 도
>   기본값이었다: max_connections 200 / shared_buffers 768MB / random_page_cost 1.1.
> - **§2**: llm 16 / memory 6 / docs 6 / **community 6** / **crawl 12** / misc 16 = 62.
>   `uploads.store(lane=…)` 로 **호출자가 부류를 선언**한다(커뮤니티 이미지가 docs 풀을
>   쓰던 오배분 해소). 레인별 `MEMORA_POOL_<NAME>` 로 배포 없이 재조정.
> - **§3**: 하한을 **활성 레인에만** 적용하는 방식으로 구현. 상한/하한은 풀 크기의 분수라
>   API(40)와 워커(16)에 같은 표가 맞는다. `_LaneGate` 참조.
> - **§4**: CONCURRENCY 8, CLASS_LIMITS 는 CONCURRENCY 에서 파생, `RESERVED={interactive:1}`.
>   `crawl.*` 는 접두사로 집계·제외되므로 핸들러가 없어도 상한이 선다.
> - **§5**: chat 120s / docs·worker 300s / community·public·admin 15s / other 60s, `SET LOCAL`.
> - **§6**: `process_stats` 테이블 + 프로세스별 스냅샷 + 관리자 [트래픽] 화면의 [프로세스]
>   표. 켜자마자 버그 2건이 드러났다 — 워커의 `loop_lag()` 가 감시자 미설치로 "가동 시간"을
>   보고하던 것, API 프로세스 키가 컨테이너 hostname 이라 배포마다 용량이 중복 집계된 것.
> - **§7**: 커뮤니티 계정당 읽기 120/분·쓰기 10/분. 계획대로 **실측 후** 정했다(24시간 동안
>   가장 바쁜 실제 호출자가 분당 1회 미만 → 약 100배 여유).

> 목표: **비서·관리자 / 커뮤니티 / 배치** 세 종류의 일이, 하나가 폭주해도 나머지를 파괴하지
> 못하게 한다. 수단은 컨테이너 분리가 아니라 **모든 경합 자원에 명시적 배분**이다.

## 0. 왜 분리가 아닌가 — 실측 근거

세 가지를 재고 나서 내린 결론이다.

**(1) 지금 있는 컨테이너조차 서로를 보호하지 않는다.**

```
memora-backend  cpus=0 mem=0     memora-worker   cpus=0 mem=0
memora-postgres cpus=0 mem=0     memora-frontend cpus=0 mem=0
```

`0`은 무제한이다. 게다가 이 호스트는 **18개 컨테이너 3개 스택**(memora·ragb·odysseus)이
4 CPU / 11.7GB를 공유하며, 제한이 걸린 것은 `odysseus-runner-1`(4GB) 하나뿐이다. 즉 오늘
memora 워커가 폭주하면 memora 백엔드뿐 아니라 **memora-postgres와 옆 스택까지** 굶는다.

여기에 커뮤니티 컨테이너를 무제한으로 하나 더 추가하면 호스트를 먹을 수 있는 경로가 네 개로
늘어날 뿐이다. **제한 없는 분리는 격리가 아니라 파편화다.**

**(2) 배치는 이미 분리되어 있다.** `memora-worker`가 18종 작업을 도는 별도 컨테이너이고,
종류별·클래스별 슬롯 상한도 여기 있다. 맛집 지도 크롤링은 새 컨테이너가 아니라 이 워커의
새 핸들러(+ 클래스)로 들어간다.

**(3) 커뮤니티 분리의 이득은 이벤트 루프 하나뿐이다.** 실측한 결합도:

```
api/community.py      → core.{deps,errors,security}, data.*, models,
                        services.{community, settings, objectstore}
services/community.py → core.errors, data.*, models, services.{inbox, profile, settings}
파이프라인·LLM·메모리 의존: 0건       역방향(비서 → 커뮤니티): 0건
```

분리는 쉽다. 하지만 얻는 것은 **이벤트 루프 격리 하나**이고, 잃는 것은 아래 §5에 적은
관측 가능성과 연결 수 예산이다. 루프 블로킹은 이미 구조적으로 막아 뒀다(`asyncio.to_thread`
전면 금지 + 가드 테스트, 명명된 스레드 풀). 남은 이득에 비해 비용이 크다.

`plan/29-community.md` §1의 "MSA로 떼지 않는다"는 판단은 유효하다 — 단, 그 근거는 *DB까지*
쪼개는 경우였다. 같은 DB·별도 프로세스는 다른 얘기이며, 트래픽이 실제로 요구하면 그때
그 문서의 세 봉합선을 따라 자르면 된다. **지금은 아니다.**

## 1. 세 부류와, 각 자원의 주인

배분은 "자원을 실제로 소유한 층"에서만 집행된다. 어느 층도 다른 층의 몫을 대신 지킬 수 없다.

| 경합 자원 | 집행 위치 | 오늘 | 문제 |
|---|---|---|---|
| 호스트 CPU·메모리 | docker compose | **없음** | 한 컨테이너가 호스트 전체를 먹을 수 있다 |
| 이벤트 루프 | 프로세스 | 백엔드 = 비서+관리자+커뮤니티 공유 | 블로킹은 막았으나 CPU 바운드는 여전히 공유 |
| 스레드 풀 | `core/pools` | llm 8 / memory 4 / docs 4 / misc 8 | **커뮤니티 이미지가 `docs` 풀을 쓴다** — 지식 색인과 직접 경합 |
| DB 연결 | `core/database` | 프로세스당 10+20, lane당 상한 50% | **상한만 있고 하한이 없다** — 커뮤니티가 굶을 수 있다 |
| Postgres 자체 | Postgres | `max_connections=100`, 역할 상한 없음 | 프로세스가 늘면 예산 초과 |
| 워커 슬롯 | `worker/__main__` | 4슬롯, 클래스 상한 `{docs: 2}` | 클래스가 하나뿐, 대화형 작업의 몫이 보장되지 않음 |
| 쿼리 시간 | Postgres | 전역 `statement_timeout=120s` | 커뮤니티 목록 쿼리에 2분은 과하다 |
| 요청 수 | 앱 레이트리밋 | 일부 엔드포인트 | 부류별 예산이 없다 |

## 2. 발견된 구체적 오배분

계획의 출발점은 취향이 아니라 이 네 가지다.

1. **커뮤니티 이미지가 지식 색인의 스레드를 쓴다.**
   `services/uploads.py:140` — `pools.to_thread("docs", _resize_image, …)`.
   커뮤니티에 이미지 몇 장이 올라가면 문서 추출·임베딩이 그만큼 밀린다. 사용자가 말한
   "하나의 심각한 자원 사용이 다른 것을 파괴"의 교과서적 사례이고, 배분만으로 고쳐진다.

2. **DB lane에 하한이 없다.** `MAX_LANE_SHARE = 0.5`는 *상한*이다. 채팅이 15개를 쥐고
   문서가 15개를 쥐면 커뮤니티는 0개다. 상한은 독점을 막지만 **몫을 보장하지 않는다.**

3. **워커 클래스가 하나뿐이다.** `CLASS_LIMITS = {"docs": 2}`. 알림 발송(`notify.send`,
   `mail.send`) 같은 짧고 사용자가 기다리는 작업이 긴 작업 뒤에 줄을 설 수 있다.

4. **관측이 프로세스 단위다.** 진행 중 요청·스레드 풀·DB 풀·LLM 매니저·세션은 모두
   in-memory라 **요청을 받은 프로세스 것만** 보인다. 배분을 넣어도 지켜지는지 볼 수 없다.

## 3. 단계

각 단계는 독립 배포 가능하고, 각자 검증 기준을 가진다.

### 1단계 — 호스트 예산 (반나절, 효과 최대)

compose에 상한과 예약을 넣는다. 상한은 과점유를 막고, 예약은 Postgres가 마지막에 굶게 한다.

| 서비스 | `cpus` | `mem_limit` | `mem_reservation` | 근거 |
|---|---|---|---|---|
| postgres | 1.5 | 2G | 768M | 모두가 의존, 예약으로 보호 |
| backend | 1.5 | 2G | 512M | 요청 처리 |
| worker | 1.0 | 1.5G | 256M | 배치는 느려도 되지만 굶기면 안 됨 |
| frontend | 0.5 | 512M | 128M | 현재 74MB |
| seaweedfs | 0.5 | 512M | 128M | 현재 130MB |
| nginx | 0.25 | 128M | 64M | 현재 7MB |

합계 상한 5.25 CPU는 4 CPU를 초과한다 — 상한은 예약이 아니므로 **의도된 오버서브스크립션**이다.
어떤 컨테이너도 혼자 호스트를 먹지 못하는 것이 목적이고, 평시 총사용량은 650MB다.
compose v2 비스웜 키(`cpus` / `mem_limit` / `mem_reservation`)를 쓴다.

> 검증: `docker inspect`로 전 컨테이너 `NanoCpus`/`Memory` ≠ 0. 워커에 CPU 폭주 부하를
> 걸고 `/api/health` p95가 평시 대비 2배 이내, Postgres 연결 정상.

### 2단계 — 스레드 풀 재배분 (2시간)

커뮤니티에 자기 풀을 준다. 총 스레드 수는 4 CPU에 맞춰 유지한다.

```
현재:  llm 8 / memory 4 / docs 4 / misc 8              = 24
제안:  llm 8 / memory 4 / docs 4 / community 3 / misc 6 = 25
```

`uploads.store`가 호출자의 부류를 받아 이미지 리사이즈를 해당 풀에서 돌린다(커뮤니티 업로드
→ `community`, 지식 문서 → `docs`). 기존 `to_thread("docs", …)` 호출부는 그대로 둔다.

> 검증: 커뮤니티 이미지 20장 동시 업로드 중 `knowledge.index` 처리 시간이 평시 대비
> 1.5배 이내. 대시보드 스레드 풀 패널에 `community`가 차고 `docs`는 비어 있어야 한다.

### 3단계 — DB 연결 예산: 상한 + **하한** (하루)

lane마다 **보장 하한**과 상한을 준다. 하한 합계 ≤ 풀 크기여야 한다.

| lane | 하한 | 상한 | 비고 |
|---|---|---|---|
| chat | 6 | 14 | 가장 비싸고 가장 중요 |
| community | 4 | 10 | 굶지 않는 것이 이 계획의 목적 |
| public | 2 | 8 | 방문자 |
| admin | 2 | 6 | 사람 하나 |
| docs | 2 | 6 | 느려도 되는 일 |
| other | 2 | 8 | |
| **합계 하한** | **18** | | 풀 20(8+12) 안 |

구현: lane별 세마포어(상한)에 **예약 슬롯**을 더한다. 예약분은 그 lane만 가져갈 수 있고,
나머지는 공용. 한도 초과는 지금처럼 대기 후 503(`lane_saturated`)이다.

Postgres 쪽 백스톱: `ALTER ROLE memora CONNECTION LIMIT 60`, `memora_dbview` 5.
프로세스별 풀은 backend 8+12, worker 5+5로 명시해 총 30 + 예비.

> 검증: 채팅 lane을 상한까지 채운 상태에서 커뮤니티 요청 20건이 전부 200. `pg_stat_activity`
> 총 연결이 예산 안. 진단 → 데이터베이스 탭의 lane 막대에 하한선이 보인다.

### 4단계 — 워커 클래스와 하한 (하루)

부류를 넷으로 하고, 대화형 작업에 슬롯을 예약한다.

```
CONCURRENCY = 6                       (현재 4)
CLASS_LIMITS = {docs: 2, community: 1, crawl: 2, interactive: 3}
KIND_CLASS   = {knowledge.index: docs, retention.*: docs,
                community.rank: community,
                crawl.*: crawl,                       ← 맛집 지도가 들어갈 자리
                notify.send: interactive, mail.send: interactive, admin.notify: interactive}
RESERVED     = {interactive: 1}        ← 이 슬롯은 긴 작업이 절대 못 가져간다
```

크롤링은 새 컨테이너가 아니라 `crawl` 클래스다. 성격이 더 갈리면 같은 이미지를
`KINDS=crawl.*` 필터로 한 번 더 띄운다(코드 변경 0).

> 검증: `crawl.*` 20건을 큐에 넣은 상태에서 `notify.send`가 30초 내 처리. 워커·작업 화면의
> 클래스 막대가 상한에 닿아도 `interactive`는 여유가 남는다.

### 5단계 — 부류별 쿼리 시간 (2시간)

전역 120초는 커뮤니티 목록 쿼리에 과하다. lane별로 준다.

| lane | statement_timeout |
|---|---|
| chat | 120s (도구가 오래 걸릴 수 있음) |
| community / public / admin | 15s |
| docs / worker | 300s |

`core/database.manager.session(lane)`이 lane에 맞는 값을 `SET LOCAL`로 넣는다.

> 검증: 커뮤니티 lane에서 `pg_sleep(20)` 상당의 쿼리가 15초에 끊긴다. 진단 → 오래 열린
> 트랜잭션 표에 15초 넘는 커뮤니티 항목이 남지 않는다.

### 6단계 — 배분을 볼 수 있게 (하루)

배분은 지켜지는지 보이지 않으면 지켜지지 않는다. 프로세스마다 자기 live 스냅샷(스레드 풀 /
DB lane / LLM / 진행 중 요청 수)을 짧은 주기로 한 행에 쓰고, 관리자 화면이 **합산**한다.
집계 지표(`api_requests`·`jobs`)는 이미 DB 기반이라 그대로다.

부수 효과: 지금 반쪽인 워커 쪽 가시성이 생긴다 — 워커의 스레드 풀과 DB lane은 오늘 어떤
화면에도 나오지 않는다.

> 검증: 워커만 부하를 받는 동안 진단 화면에 워커의 풀 점유가 보인다. 프로세스를 하나 더
> 띄우면 합계가 늘어난다.

### 7단계 — 부류별 요청 예산 (선택, 반나절)

커뮤니티 엔드포인트에 사용자·IP당 예산을 둔다(목록 60/분, 작성 10/분 수준). 스크레이퍼가
백엔드의 요청 처리량을 독점하지 못하게 하는 마지막 층이다. 트래픽 대시보드의 "호출자" 표가
이미 누가 얼마나 부르는지 보여주므로, 값은 실측 후 정한다.

## 4. 하지 않는 것

- **컨테이너를 쪼개지 않는다** — 위 §0. 트래픽이 요구하면 `plan/29` 봉합선을 따라 자른다.
- **DB를 쪼개지 않는다** — 작성자 신원이 `users`와 매 요청 조인된다.
- **k8s로 가지 않는다** — 단일 머신에 3개 스택. compose 상한으로 충분하다.
- **Redis를 도입하지 않는다** — 레이트리밋·캐시는 프로세스 로컬 + 20초 TTL로 족하다.

## 5. 순서가 중요한 이유

1단계가 먼저다. **제한이 없으면 나머지 배분은 호스트 레벨에서 무의미하다** — 워커가 4 CPU를
다 쓰는 동안 lane 하한은 연결을 보장해도 그 연결로 아무 일도 못 한다. 반대로 1단계만 해도
"한 부류가 호스트를 파괴하는" 최악은 사라진다.

6단계는 3·4단계보다 먼저 해도 좋다. 배분을 넣고 나서 효과를 못 보면 튜닝이 추측이 된다.

## 6. 남은 미결정

- `interactive` 예약 슬롯을 워커 6슬롯 중 1로 둘지 2로 둘지 — 실측 후.
