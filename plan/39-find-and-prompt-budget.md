# 39. 비서 찾기(이름 → 상대 비서) + 프롬프트 예산 정리

2026-09-13. plan/38 의 릴레이는 "링크를 아는" 상대에게만 갈 수 있었다. 이 문서는 (1) 오너가 이름만 말해도 비서가 상대 비서를 찾아 **확인을 받은 뒤** 말을 걸게 하고, (2) 그 과정에서 프롬프트가 더 길어지지 않도록 **프롬프트 전체를 예산 안으로 정리**한 기록이다.

## 1. 비서 찾기

| 단계 | 근거 | 동작 |
|---|---|---|
| ① | 오너가 링크(URL/코드)를 줌 | 그대로 `secretary_ask` |
| ② | 내 인맥의 회원 노드 / 친구 링크 / 내 비서를 방문한 회원 | `secretary_find(name)` 이 이름·별칭 **부분 일치**로 찾음. 근거(인맥·친구·방문)와 공개 프로필의 직함·소속을 붙여 후보 카드 |
| ③ | 디렉터리(계정 표시 이름·닉네임, 2자 이상) | "아는 분 중엔 없는데, 혹시 이 분인가요?" |

- 후보가 되려면 상대 비서에 **활성 링크 + 다른 비서의 문의 받기 + 이름으로 찾아올 수 있게** 세 스위치가 켜져 있어야 한다. 회원은 찾았지만 닿을 수 없으면 그렇게 말한다.
- **보내기 전 확인은 서버가 강제한다.** 찾기 결과는 `relay_candidates` 에 (대화, 턴) 과 함께 남고, 그 후보로 보내려면 **찾기와 다른 턴**(= 오너가 한 번 더 말한 뒤)이어야 한다. 모델이 확인을 건너뛰면 `confirm_first` 오류가 돌아온다. 링크 코드를 직접 넘겨도 그 코드가 이 대화의 후보였다면 같은 규칙.
- 상대별 상한: 같은 오너 → 같은 **비서** 하루 2건(`relay_target_cap`, 링크가 여럿이어도 같은 문). 커뮤니티 글의 반익명 정체성은 검색 대상이 아니다.
- 이름 매칭은 계정 표시 이름·닉네임(디렉터리)뿐 아니라 **공개로 표시된 프로필 이름(부르는 이름·이름)** 도 본다 — 사람들은 프로필 이름으로 서로를 안다. 비공개 프로필 이름은 검색되지 않는다. 같은 대화에서 같은 사람을 다시 찾으면 **이전 후보를 그대로 돌려준다**(모델이 확인 턴에 재검색해도 "이전 턴에 찾음" 시계가 유지됨). 발신이 거부되면 실패 카드 + `sent:false` 로 모델이 "보냈다"고 말하지 못하게 한다(실측에서 그렇게 거짓말한 사례가 있었다).
- 후보 카드의 [이 비서에게 보내기] 는 채팅에 확인 문장을 넣는다 — 그 문장이 곧 오너의 확인 턴이다.

## 2. 프롬프트 예산 (측정 → 정리)

배포 전 실측(관리자 제니, 시스템 프롬프트만): 오너 6,178자(≈2.5k 토큰), 방문자 7,711자(≈3.1k). 여기에 턴마다 사실 최대 4,000자 + 관계 1,067자 + 기억 2,400+1,000자 + 라이브 블록이 붙었다. 도구 설명(3,620자)은 도구 스키마로 **한 번 더** 전달되고 있었다.

정리 원칙
1. **한 사실은 한 곳에.** 도구 사용법은 도구 설명(스키마)에만. 시스템 프롬프트 3장은 "정확한 이름으로 부른다·짐작 대신 조회·카드는 한 문장으로 확인·(방문자) 비공개에 닿는 도구는 없다" 네 줄.
2. **바뀌지 않는 것은 앞(캐시), 바뀌는 것만 뒤.** 관계의 안전선은 오너 규칙(5장)에 세 줄로 한 번; 턴마다 가는 관계 블록은 상태만(≤300자). 릴레이 규칙은 빌드 때 고정 섹션(`base_relay`)으로 한 번; 턴마다 가는 릴레이 블록은 "n/최대, 남은 수, 마지막이면 닫아라"만.
3. **같은 말을 세 번 하지 않는다.** 방문자 규칙(5장)은 2,812자 → 약 1,400자. "이 사람은 오너가 아니다"는 한 번, 예시 문구는 한 줄, 공개/비공개는 두 줄.
4. **볼륨 상한을 코드로.** 사실 블록 40줄/4,000자 → 30줄/2,500자. `tests/test_prompt_budget.py` 가 섹션별 상한과 중복 문장을 검사한다.
5. **보이게 한다.** 지시문 미리보기에 섹션별 글자 수.

정리 후 목표: 오너 ≤ 4,300자, 방문자 ≤ 5,000자(도구 설명 제외), 턴당 volatile ≤ 6,000자.
