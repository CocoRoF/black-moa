> **§2 의 판단 4(사실을 [내 정보] 로)와 판단 6(연동을 [내 정보] 로)는 틀렸다.**

## 0. 세 당사자

```
 [사용자 정보]  ──전부──▶  [비서]  ──공개 범위만큼──▶  [외부인]
      원장                   읽는 자                    듣는 자
                              │
                        [비서의 기억]  ← 여기서 생기고 여기 산다
```

네 가지 규칙으로 줄인다.

1. **원장은 하나.** 내 정보는 전부 [내 정보] 아래 있다 (+ 커뮤니티에 쓴 내 글).
2. **비서는 원장을 전부 본다.** 비서가 무엇을 보느냐를 고르는 설정은 **없앤다.**
3. **공개 범위는 원장의 각 항목에 붙는다.** [모두 공개] · [내 인맥에게만] · [비공개].
4. **기억은 원장이 아니다.** 대화에서 생겨 그 비서의 금고에 살고, 밖으로 나갈지는
   기억 쪽에서만 정한다.

이 넷을 지키면 주인이 답해야 할 질문이 딱 두 개로 준다.
**"내 무엇이 있나"**(원장) 와 **"그게 누구까지 가나"**(그 항목의 범위).

## 1. 지금 무엇이 어긋나 있나

### 1-1. 같은 3단계를 다섯 가지 말로 부른다

| 원천 | 지금 쓰는 값 | 중간 단계 |
|---|---|---|
| 프로필 | `public` / **`known`** / `private` | **있음** |
| 피드·블로그 글 | `public` / **`friends`** / `private` | **있음** (이름만 다름) |
| 사실 | `public` / `private` / `visitor_private` (+ 레거시 `on_request`) | **없음** |
| 지식 문서 | `public` / `private` | **없음** |
| 인맥 노드 | `public` / `private` | **없음** |

`known` 과 `friends` 는 같은 뜻이고, 나머지 셋은 중간이 아예 없다.

### 1-2. 중간 단계가 살아 있는 곳은 프로필뿐이다

턴마다 보는 사람의 거리를 실제로 잰다. 이건 **제대로 돼 있다.**

```python
# pipeline/runner.py:391
viewer = "owner" if rt.audience != "visitor" else await PPL.viewer_level(
    db, owner.id, visitor.user_id if visitor is not None else None)
```

`viewer_level` 은 서로 맺은 인맥이거나 같은 회사를 서로 인증했으면 `known`,
아니면 `stranger` 다. **로그인만 했다고 인맥이 되지는 않는다.** 정확한 판단이다.

그런데 이 `viewer` 를 쓰는 곳은 `render_profile` **하나뿐**이다. 나머지는 전부
"주인이냐 아니냐" 두 갈래로만 갈린다.

```python
_facts_block   : 방문자면 visibility == "public" 인 것만
knowledge.search: 방문자면 d.visibility = 'public' 인 것만
network 필터    : audience == "owner" or n.visibility == "public"
blog.sync      : level = "public" if post.visibility == "public" else "private"
```

**결과.** 내 인맥이 공개 링크로 내 비서에게 말을 걸면, 프로필의 [인맥에게만] 칸은
보이는데 **[인맥에게만] 쓴 글도, 그 범위의 지식도, 인맥 정보도 하나도 안 간다.**
마지막 줄이 특히 나쁘다. `friends` 로 쓴 글이 지식 문서가 될 때 `private` 으로
납작해져서, 그 글은 **영원히** 인맥에게 못 간다. 원본에는 `friends` 가 남아 있는데
비서 쪽 사본에는 그 값이 없다.

### 1-3. "비서가 보느냐" 를 고르는 설정이 셋 있다

규칙 2를 어기는 것들이다.

| 설정 | 어디 | 끄면 |
|---|---|---|
| 비서에게 인맥 정보 제공 (`users.network_to_secretary`) | 인맥 › 설정 | 인맥 요약도 도구도 **전부** 사라짐 |
| 비서 능력 [지식] (`capabilities.knowledge`) | 비서 › 설정 | 지식 문서를 **아예** 못 봄 |
| 비서 정책 `profile_fields` | 비서 › 설정 | 프로필 칸 범위를 두 번째로 정함 |

앞의 둘은 **원천을 끊는 스위치**다. 세 번째는 범위를 정하는 것이라 성격이 다르지만,
[내 정보] 와 **같은 질문에 두 군데서 답하는** 문제가 있다.

### 1-4. 사실은 주인 것인데 비서 밑에 있다

읽을 때는 `Fact.owner_id` 만 본다. 곧 제니가 알게 된 사실이 다른 비서에게도 간다.
**이건 규칙 2 대로 맞다.** 틀린 것은 화면이 `/app/agents/{id}/memory` 라는 점이다.
비서가 셋이면 같은 목록이 세 군데 보이고, 어디서 지워도 셋 다에서 사라진다.

(plan/47 §3 과 같은 결론이다.)

### 1-5. 기억은 이미 제자리에 있다

금고는 비서별이고(`vault_root(agent.id)`), 방 셋으로 나뉜다.

| 방 | 주인 턴 | 방문자 턴 |
|---|---|---|
| `owner` | 읽고 씀 | **못 읽음** |
| `shared` | 읽음 | **읽음** |
| `visitors` | 읽음 | 제 것만 읽음 |

**`shared` 가 곧 "외부 공개" 다.** 규칙 4가 요구하는 구조가 이미 있다. 부족한 것은
두 가지뿐이다. 중간 단계가 없고(인맥에게만 = 없음), 화면이 이것을 "공개 설정" 이
아니라 "칸 이름" 으로 보여 준다. 주인은 `shared` 에 넣는 것이 남에게 보여 주는
일이라는 걸 화면만 보고는 알 수 없다.

## 2. 어떻게 하는 것이 좋은가

### 판단 1 — 공개 범위는 **한 어휘**로 통일한다

`public` · `known` · `private` 셋. 화면 말로는 **[모두 공개] · [내 인맥에게만] · [비공개]**.

- 피드의 `friends` 를 `known` 으로 옮긴다(데이터 이관 한 번).
- 지식 문서·인맥 노드에 `known` 을 **추가**한다.
- 사실의 `on_request` 는 `private` 으로 접고, `visitor_private` 는 **범위가 아니라
  주인이 아닌 사람에 대한 사실**이라는 뜻이므로 범위 칸에서 빼서 별도 표시로 옮긴다.
  지금은 한 칸이 두 가지를 뜻하고 있다.

> **왜 새 값을 만들지 않고 `known` 을 쓰나.** 프로필이 이미 `known` 으로 돌고 있고
> `viewer_level` 이 그 말을 판정한다. 다른 이름을 새로 만들면 판정기를 두 벌 갖게 된다.

### 판단 2 — 거리 판정을 **모든 원천에 한 번에** 먹인다

지금 `viewer_level` 을 쓰는 곳이 하나뿐인 것이 1-2 의 원인이다. 턴이 시작될 때 잰
`viewer` 를 **모든 조회에 그대로 넘긴다.**

```
viewer = owner | known | stranger        ← 턴마다 한 번 잰다
  ├─ 프로필     render_profile(viewer)          (이미 그러함)
  ├─ 사실       _facts_block(viewer)            ← 고칠 것
  ├─ 지식       K.search(viewer)                ← 고칠 것
  ├─ 인맥       N.visible(viewer)               ← 고칠 것
  └─ 글         blog.sync_knowledge 가 범위 보존 ← 고칠 것
```

판정 규칙은 한 줄로 충분하고, 이미 있다.

```python
def visible_to(level, viewer):        # services/profile.py:130
    if viewer == "owner":  return True
    if level == "public":  return True
    return level == "known" and viewer == "known"
```

**이 함수를 공용으로 올려서 다섯 군데가 전부 이걸 부르게 한다.** 규칙이 한 군데
있으면, 다음에 원천이 하나 늘어도 같은 자리를 지나간다.

> **`private` 은 비서에게는 간다.** 규칙 2 다. `private` 이 막는 것은 **외부인에게
> 나가는 것**이지 비서가 아는 것이 아니다. 주인 턴은 지금도 범위를 안 따진다
> (`vis_clause = "" if audience == "owner"`). 그 줄이 이 설계의 심장이고, 나머지를
> 거기에 맞추면 된다.

### 판단 3 — 원천을 끊는 스위치 둘을 **없앤다**

- **[비서에게 인맥 정보 제공] 삭제.** 인맥은 원장이고, 비서는 원장을 본다. 남에게
  갈지는 노드마다의 범위가 정한다. 지금 이 토글을 끈 사람은 "남에게 안 보이게" 하려던
  것일 가능성이 높은데, 실제로는 **제 비서만 눈이 먼다.** 뜻과 효과가 어긋나 있다.
  - 옮길 곳: 같은 화면의 [내 인맥 공개] 가 이미 남에게 보이는 범위를 정한다.
    노드마다의 범위와 합쳐 **한 줄로** 만든다.
- **비서 능력 [지식] 삭제.** 같은 이유다. 보여 주기 싫으면 문서의 범위를 좁힌다.
- **비서 정책 `profile_fields` 삭제.** 칸의 범위는 `owner_profiles.visibility` 하나가
  정본이다. 기본값 표도 하나만 남긴다(지금 `DEFAULT_FIELD_VIS` 와
  `DEFAULT_DISCLOSURE` 가 `location` 에 서로 다른 기본값을 준다).

> 비서 설정에 남을 것은 **성격·말투·도구·모델·공개 링크** 다. 곧 *어떻게 말하는가*.
> *무엇을 아는가* 는 전부 [내 정보] 로 간다.

### 판단 4 — 사실을 [내 정보] 로 올린다

`[내 정보] › 사실`. 행마다 범위 세 단계. "어느 비서가 알게 됐는지" 는 꼬리표로만
남기고 범위를 가르지 않는다. 관계가 세는 사실 수도 주인 단위로 맞춘다
(지금은 읽기는 주인 단위, 세기는 비서 단위다).

### 판단 5 — 기억은 [비서] 에 두되, 공개는 **범위 칸**으로 보여 준다

방 이름(`owner`/`shared`/`visitors`)을 그대로 노출하는 대신, 기억 하나하나에
**[비공개] · [인맥에게만] · [모두 공개]** 를 붙인다. 지금의 `owner`/`shared` 가 그
양 끝이므로 중간만 더하면 된다.

**기억은 [내 정보] 로 옮기지 않는다.** 원장은 주인이 넣은 것이고, 기억은 비서가
겪은 것이다. 비서를 지우면 그 기억은 같이 사라지는 것이 맞고, 원장은 남는 것이 맞다.

### 판단 6 — 화면은 두 축으로 다시 그린다

```
[내 정보]                         [비서]
├ 프로필      ─ 범위              ├ 성격·말투
├ 사실   (신) ─ 범위              ├ 도구·모델
├ 지식        ─ 범위              ├ 공개 링크
├ 인맥        ─ 범위              └ 기억        ─ 범위
├ 내 글       ─ 범위
├ 커뮤니티 글 ─ (실명 글만, 늘 비공개)
└ 연동(구글)  ─ 원천 on/off
```

- **연동은 [내 정보] 로 올린다.** 지금 `/app/integrations` 는 왼쪽 줄 어디에도 없다.
  내 메일과 일정이 비서에게 가는데 그 스위치로 가는 길이 메뉴에 없다.
- 각 줄 옆에 **지금 무엇이 몇 개이고 그중 공개가 몇 개인지**를 적는다. 주인이
  "내 무엇이 밖으로 나가나" 를 한 화면에서 세도록.
- 비서 설정에서는 **"이 비서는 내 정보를 전부 봅니다"** 라고 한 줄로 말해 준다.
  설정이 사라진 자리에는 사실을 적어야 한다. 아무 말도 없으면 사용자는 기능이
  없어졌다고 생각한다.

## 3. 위험한 곳 하나

범위를 넓히는 작업이라, 한 번 잘못하면 **안 보이던 것이 보이게 된다.**

- 지식·인맥에 `known` 을 더할 때 **기존 행은 전부 지금 값 그대로 둔다.** `private` 을
  `known` 으로 올리는 자동 이관은 하지 않는다.
- 피드의 `friends` → `known` 은 이름만 바꾸는 것이라 안전하지만, `blog.sync_knowledge`
  가 범위를 보존하게 고치는 순간 **`friends` 글이 처음으로 인맥에게 도달한다.**
  이건 주인이 원래 `friends` 로 정한 대로 돌아가는 것이라 맞는 방향이지만,
  **배포 전에 주인에게 한 번 알려야 한다.**
- `visitor_private` 를 범위 칸에서 떼어낼 때, 떼는 동안 그 사실이 잠깐이라도
  `public` 으로 읽히면 안 된다. 기본값을 `private` 으로 두고 옮긴다.

## 4. 순서 제안

1. `visible_to` 를 공용으로 올리고 **사실·지식·인맥·글** 네 조회가 그것을 부르게 한다.
   (어휘는 아직 안 바꾼다. 중간 단계가 없는 원천은 그대로 두 단계로 동작한다.)
2. 지식·인맥에 `known` 추가, 피드 `friends` → `known` 이름 통일,
   `blog.sync_knowledge` 가 범위를 보존하게 한다.
3. 스위치 셋 제거(인맥 제공·지식 능력·비서 프로필 정책).
4. 사실을 [내 정보] 로 옮긴다.
5. 기억에 범위 칸을 붙이고 방 이름을 감춘다.
6. 연동을 [내 정보] 로 올리고, 각 줄에 개수와 공개 개수를 적는다.

1번만 해도 **공개 채팅에서 인맥이 인맥 대접을 받기 시작한다.** 가장 값이 크고 가장
작다.

### 값이 넓어진 것은 하나도 없다

범위를 넓히는 작업이라 제일 무서운 것이 "안 보이던 것이 보이게 되는 것" 이었다.
배포 전에 운영을 세었다.

- `friends` 글: **0개**. 어휘를 옮겨도 새로 닿는 글이 없었다.
- 비서 정책을 직접 손댄 칸: **1개**, 그런데 [내 정보] 에 같은 값이 있어 바뀜 없음.
- 스위치를 꺼 둔 사람: **0명**.
- `network_public`: 11명 전원 `all` → `public`. 뜻이 같은 말로 옮긴 것뿐(0063).
- 기억: `shared` 방 **0개**. 옛 기억은 전부 `private` 으로 읽혀 인맥에게도 0개.

### 규칙으로 못 박은 것

- **모르는 값은 가장 좁은 쪽으로.** `normalize` 는 모르는 범위를 `private`,
  `normalize_viewer` 는 모르는 사람을 `stranger` 로 접는다. 반대 방향의 실수는
  "왜 안 보이지" 로 끝나고, 이쪽 실수는 되돌릴 수 없다.
- **새 기억은 안 고르면 비공개.** 고르지 않은 것이 공개되면 안 된다.
- **도구도 같은 벽을 지난다.** 블록만 막고 도구를 열어 두면 비서에게 "찾아보라" 고
  시키는 것만으로 벽을 넘는다.
- **`visitor_private` 는 범위가 아니다.** 그 손님에 대한 사실이라는 표시다. 범위 칸을
  주지 않는다: 바꾸게 두면 손님 얘기가 주인의 원장이 된다.
- **손님 방은 제 것만.** 인맥이어도, [모두 공개] 라고 적혀 있어도 남의 손님 기록은
  못 본다. 그건 범위 문제가 아니라 사고다.

### 비서 설정에 남은 것

**어떻게 말하는가**만 남았다. 성격·말투·모델·도구(바깥에 일을 하는 것)·공개 링크.
**무엇을 아는가**는 전부 [내 정보] 로 갔다. 설정이 사라진 자리에는 사실을 적었다:
"내 비서는 내 정보와 지식, 인맥을 늘 볼 수 있어요."

### 아직 안 한 것

- 비서별 지식(`d.agent_id`)은 여전히 `/app/agents/{id}/knowledge` 에 따로 있다.
  원장 요약에는 전체가 잡히지만, 목록은 아직 두 군데다.
- 기억의 옛 방 `shared` 는 남겨 두었다. 운영에 0개라 화면에서는 안 보이고, 값이
  생기면 그때 보인다.
