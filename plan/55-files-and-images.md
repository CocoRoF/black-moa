# 55. 파일 — 비서가 기억하는 자료

2026-09-23. **구현 전 검토용 계획 — 3판.** 1판의 결정 다섯에 사용자가 답했고(§9), 2판에서
저장 공간(§3-3)·방문자 파일(§6-3)·붙여넣기와 끌어다 놓기(§6-1)를 구체화했다. 3판은 메신저를
**비서가 당연히 보는 곳이 아니라 허락받고 여는 곳**으로 바로잡는다(§6-4). 2판의 권장안
("보낸 사람의 비서가 자동으로 기억")은 바로 그 "당연히 보는" 구조를 새로 만드는 것이었다.

요구는 둘이다.

1. 채팅에서 이미지를 제대로 다룬다 — 붙여넣기, 사진 넣기, 끌어다 놓기. 비서 대화·메신저·
   공개 비서 세 자리 모두.
2. 비서가 **파일을 기억한다.** 채팅으로 들어온 자료를 모두 저장하는 공간(스토리지)을 두고,
   비서가 자유롭게 읽는다. 비서 화면의 [메모리] 오른쪽에 [파일] 탭.

## 0. 지금 어떻게 돼 있나 — 프로드에서 실측

### 0-1. 사진은 올라가지만 **다시 보인 적이 없다**

| 확인 | 결과 |
|---|---|
| `POST /api/uploads` (이미지) | 201. S3(seaweedfs)에 `<주인>/attachment/<id>.jpg` 로 저장 |
| `GET /api/uploads/{id}` (인증 헤더 있음) | **500** — `File at path s3://memora/… does not exist` |
| 같은 주소를 `<img src>` 로 (헤더 없음) | **401** |

저장소를 S3 로 옮길 때 이 읽기 경로만 로컬 파일(`FileResponse`)로 남았다. 그리고 `<img>`
태그는 인증 헤더를 보낼 수 없어서, 고쳐도 채팅 기록의 사진은 401 이 된다. 광장 사진은
이미 **서명 주소**로 이 문제를 풀었는데(plan/51 전후, `community/images/{id}?t=`), 채팅은
그 길을 타지 않았다. 운영 전체에서 첨부가 달린 메시지는 **3건**뿐이다 — 기능이 사실상
안 쓰였고, 쓰였어도 보이지 않았다.

### 0-2. 첨부는 **그 한 턴에만** 존재한다

`pipeline/runner._build_input`: 이미지는 base64 로 그 턴의 모델 입력에 실리고(최대 4장),
문서는 추출한 글을 12,000자까지 본문에 붙인다. 메시지에는 `upload_id·파일명·형식`만
남는다. **다음 턴부터 비서는 그 파일을 다시 볼 방법이 없다.** "아까 보낸 사진 다시 봐 줘"
에 답할 수 없는 구조다 — 요구 2 의 핵심 공백.

### 0-3. 입력 자리마다 다르다

| 자리 | 첨부 | 붙여넣기 | 끌어다 놓기 |
|---|---|---|---|
| 비서 대화 (`OwnerChat`) | 📎 만 | ✗ | ✗ |
| 메신저 (`MessengerDock`) | ✗ (API 는 `attachments` 를 받는데 화면이 늘 `[]`) | ✗ | ✗ |
| 공개 비서 (`PublicChat`) | ✗ (방문자용 업로드 경로 자체가 없음) | ✗ | ✗ |

### 0-4. 그 밖에 걸리는 것

- **아이폰 사진(HEIC)** 이 허용 형식에 없다 → 아이폰에서 찍은 사진은 `unsupported_type`.
- **비전이 없는 모델**에 이미지를 보내도 막지 않는다. 카탈로그에 `supports_vision` 이
  있지만 파이프라인이 읽지 않는다 — Geny 에서 겪은 "vision 은 조용히 깨진다" 와 같은 모양.
- [지식] 에도 파일이 있다(`knowledge_documents`, 요금제별 `max_knowledge_mb`). 둘의
  경계를 정하지 않으면 같은 자료가 두 곳에 산다.

## 1. 참고한 것 — Geny · XGEN agent-xgeny 에서 배운 규칙

| 출처 | 규칙 | 여기서 |
|---|---|---|
| Geny 파일 뷰어 | 읽는 길을 셋으로: **목록 / 원본 바이트 / 글(상한 2MB·20,000줄)** + 문서 미리보기. 형식→종류 표 **하나**로 가른다. | §4 서빙, §6 화면 |
| Geny 파일 뷰어 | 담장 규칙(누가 무엇을 읽나)은 **한 함수**에만. | §5 `files.visible_to` |
| XGEN 첨부 경로 계약 | 경로를 말하는 자격은 **기준을 아는 쪽 하나**. 기준이 다른 문구 셋이 섞여 모델이 경로를 지어냈다. 도달 못 하는 경로는 말하지 않는다. | 비서에게는 **경로를 주지 않고 파일 id** 만 준다 |
| XGEN 첨부 경로 계약 | 이미지는 턴을 열 때 바이트를 싣고, 문서는 싣지 않고 **도구로 읽게** 한다. | §5 |
| XGEN 대화별 격리 | 공개(배포)된 에이전트는 **대화마다 자기 파일 칸**. 한 사람이 올린 것을 옆 대화가 읽던 사고. 회수(명시적 삭제 + 유휴 기한)가 설계의 반. | §3 방문자 격리·보존 |
| XGEN 업로드 버전 | 저장 키에 **고유 id** 가 없으면 같은 이름이 서로를 덮는다. 결정은 저장 **앞**. | 키는 이미 `<주인>/<종류>/<id>` — 유지 |

## 2. 원칙

1. **한 저장소, 세 입구.** 비서 대화·메신저·공개 비서로 들어온 첨부는 전부 한 원장
   (`agent_files`)에 **자동으로** 남는다. 주인이 따로 "저장" 을 누르지 않는다.
2. **파일과 지식은 다르다.**
   - [지식] = 주인이 **골라서** 준 참고 자료. 검색 색인·공개 범위가 붙는다.
   - [파일] = 대화로 **들어온** 모든 자료. 원본 그대로 보관, 기본 비공개.
   - 비서는 둘 다 읽는다. 파일을 [지식으로 올리기] 하면 지식이 된다(복사가 아니라 승격).
3. **비서에게는 경로가 아니라 파일 id 를 준다.** 비서가 파일을 여는 길은 도구 하나이고,
   그 도구가 id 로 찾는다. 경로를 말하는 자리를 없애면 경로를 지어낼 자리도 없다.
4. **누가 무엇을 읽나는 한 함수가 정한다** (`files.visible_to`). 주인 대화는 주인의 모든
   파일, 방문자 대화는 **그 방문자가 올린 것 + 주인이 공개한 것**만. 메모리의 방문자 칸
   규칙(`facade._visible`)과 같은 모양으로 둔다.
5. **조용히 깨지지 않는다.** 비전 없는 모델이면 이미지를 캡션 글로 바꿔 넘기고, 그 사실을
   기록한다. 추출이 실패한 문서는 "읽을 수 없는 파일" 로 보이고 비서도 그렇게 안다.

## 3. 데이터

### 3-1. `agent_files` (신규)

| 열 | 뜻 |
|---|---|
| `id`, `owner_id`, `agent_id` | 누구 비서의 파일인가 |
| `upload_id` | 바이트가 있는 곳 (`uploads` 재사용 — 저장 방식은 그대로) |
| `source` | `chat` · `messenger` · `public` · `manual` |
| `scope` | `owner` 또는 `visitor` (+ `visitor_id`) — §2-4 |
| `conversation_id`, `message_id` | 어느 대화의 어느 말과 함께 왔나 (파일 → 대화로 돌아가기) |
| `filename`, `mime`, `kind` | `kind` = image · pdf · document · sheet · slides · text · audio · other (형식→종류 표 하나) |
| `size_bytes`, `sha256` | 같은 비서·같은 칸에서 같은 바이트는 **한 행** (여러 번 붙여 넣어도 하나) |
| `caption` | 이미지 한두 문장 설명 (비전 모델이 한 번 씀) — 검색·비전 없는 모델용 |
| `text_chars`, `pages`, `status` | 추출 결과. `status` = pending · ready · unreadable |
| `thumb_upload_id` | 목록·말풍선용 작은 그림 |
| `visibility` | 기본 `private`. 공개하면 방문자 대화에서도 쓸 수 있다 (plan/48 의 어휘) |
| `deleted_at` | 지우면 비서도 더는 못 본다. 원본은 보존 기간 뒤 정리 |

추출한 **본문**은 행에 두지 않는다. 바이트와 나란히 객체 저장소에 `…/<id>.txt` 로 둔다
(대용량 텍스트를 DB 에 싣지 않는다).

### 3-2. 저장 흐름

```
업로드(3 입구) ─▶ uploads (바이트, 형식 검사·EXIF 제거·HEIC→JPEG)
             ─▶ agent_files 행 (pending) ─▶ 작업 files.ingest
                  · 문서: 글 추출(기존 extract, 격리 자식 프로세스) → .txt
                  · 이미지: 썸네일 + 캡션(트리거 모델처럼 작은 비전 모델, 집이 냄)
                  · 결과 → status ready / unreadable
```

- **할당량**: 지식과 **합쳐서** 하나의 저장 한도로 관리한다 (§3-3, 결정 1).
- **보존**: 주인 파일은 지울 때까지. 방문자 파일은 그 비서의 방문자 보존 기간(`retention_days`,
  기본 90일)을 따른다 — 기존 `retention.sweep` 에 한 줄 더한다.

### 3-3. 저장 공간 — 한 한도, 나눠서 보이기 (결정 1)

**한도는 계정에 하나다.** 지식 저장소와 비서마다의 파일이 같은 한도를 나눠 쓴다. 지금의
`plans.max_knowledge_mb` 를 `max_storage_mb` 로 넓힌다(이름만 바꾸는 이관, 값은 요금제
화면에서 관리자가 정한다). 지금 값은 Free 50MB 라 사진 몇 장이면 찬다 — 새 기본값은
**Free 1GB · Pro 3GB** (결정 1-a). 관리자는 요금제 화면에서 바꿀 수 있다.

**무엇이 한도를 쓰나**

| 칸 | 세는 것 |
|---|---|
| 지식 저장소 | `knowledge_documents` 의 파일 |
| 비서마다 (예: 제니, 미관리비서) | 그 비서의 `agent_files` — 주인 대화 + 그 비서에게 온 방문자 파일 |
| 메신저 | 사람끼리 방에 **내가 올린** 파일. 비서의 파일이 아니다(§6-4) |
| 기타 | 프로필 사진, 소식에 올린 사진, 광장 사진 등 위에 속하지 않는 업로드 |

지운 파일은 30일 보관(결정 5) 동안에도 **한도에서 뺀다** — 지운 것 때문에 새 것을 못 올리면
지운 의미가 없다. 원본은 30일 뒤 실제로 지운다.

**보이기 — 사용자가 보여 준 구글 저장 공간 모양 그대로**

```
2.4GB / 3GB (81%) 사용 중
████████████████████▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░█
● 지식 저장소   ● 제니   ● 미관리비서   ● 메신저   ● 기타

[여유 공간 확보]   [저장 공간 늘리기]
```

- 막대 하나를 칸 수만큼 나눠 칠한다. 색은 칸마다 고정(같은 비서는 어디서나 같은 색).
- **칸에 올려 두면 정확한 용량**을 보여 준다: `제니 — 1.23 GB (1,234,567,890 바이트) · 파일
  132개 · 방문자 파일 41개`. 공통 호버 부품(`components/ui/hover-card`)을 쓴다. 범례의 점에
  올려 두어도 같은 카드.
- 너무 작아 안 보이는 칸도 최소 폭 2px 로 그려 올려 둘 자리를 만든다.
- **어디에 서나**: 계정 쪽 [내 정보] 아래 **[저장 공간]** 이 정본 화면. 같은 막대의 한 줄
  요약이 [지식] 탭과 [파일] 탭 위에도 선다(그 탭의 칸을 강조).
- [여유 공간 확보] → [파일] 탭을 **큰 파일 순**으로 연다. [저장 공간 늘리기] → 요금제.

**가득 차면**: 90% 에서 알린다(인박스 + 화면 띠). 100% 면 **새 업로드를 받지 않는다** —
채팅은 계속되고, 첨부만 "저장 공간이 가득 찼어요" 로 거절한다. 방문자에게는 주인 사정을
말하지 않고 "지금은 파일을 받을 수 없어요" 라고만 한다(plan/53 과 같은 규칙). 조용히
오래된 것을 지우지 않는다 — 사용자 자료를 사용자 모르게 지우는 일은 없다.

## 4. 서빙 — 읽는 길 넷

| 길 | 쓰임 | 비고 |
|---|---|---|
| `GET /api/files?…` | 목록 (거르기: 기간·출처·종류·검색) | [파일] 탭 |
| `GET /api/files/{id}/raw?t=<서명>` | 원본 바이트 | **서명 주소** — `<img>`·새 창·다운로드가 헤더 없이 연다. 광장 사진과 같은 방식, 유효 12시간 |
| `GET /api/files/{id}/thumb?t=` | 썸네일 | 말풍선·목록 |
| `GET /api/files/{id}/text` | 추출 글 | 상한 2MB(Geny), 넘으면 `truncated:true` |

- 바이트는 **객체 저장소에서 스트리밍**한다 (지금 500 을 내는 `FileResponse` 경로를 없앤다).
- 메시지·목록 응답은 서명 주소를 **내려준다** — 화면이 주소를 만들지 않는다.
- 방문자도 같은 길을 쓴다: 방문자 토큰으로 발급받은 서명 주소는 그 방문자 칸 파일에만.

## 5. 비서가 읽는 길

### 5-1. 도구 셋

| 도구 | 하는 일 |
|---|---|
| `files_list(query?, kind?, since?)` | 파일 id · 이름 · 종류 · 날짜 · 캡션/첫 줄. 이름·캡션·본문 첫 부분으로 찾는다 |
| `file_read(id, page?, offset?)` | 추출 글을 한 번에 최대 N자(예: 20,000자)씩. 쪽/위치로 이어 읽기 |
| `file_view(id, page?)` | 이미지를 **다시 본다**(비전). PDF 는 쪽 그림으로. 비전 없는 모델이면 캡션을 돌려준다 |

셋 다 `files.visible_to(ctx)` 를 지나야만 파일을 연다 — 방문자 대화의 도구는 그 방문자
칸과 공개된 파일만 본다.

### 5-2. 프롬프트에 무엇을 싣나

- **올린 그 턴**: 지금처럼 이미지는 바이트로, 문서는 앞부분(12,000자)을 싣는다 — 바로
  이어지는 질문에는 도구를 거치지 않는 편이 빠르다. 다만 각 첨부에 **파일 id 를 함께**
  적어 "나중에 다시 볼 수 있다" 를 비서가 안다.
- **그 뒤 턴**: 바이트를 싣지 않는다. 짧은 파일 목록 블록(최근 10개: id·이름·캡션 한 줄)만
  싣고, 필요하면 도구로 연다. 목록 순서는 고정해 프롬프트 캐시를 깨지 않는다.
- **비전 없는 모델**: 이미지 자리에 캡션을 넣고 `(그림 설명)` 이라 표시한다.
  `supports_vision` 을 파이프라인이 처음으로 **집행**한다.

## 6. 화면

### 6-1. 입력 — 세 자리에 같은 부품

`Composer` 하나를 고치면 세 자리가 같이 바뀐다 (지난번 한 줄/두 층 작업과 같은 부품).

- **붙여넣기** — 규칙을 먼저 정해야 깨지지 않는다.
  - 클립보드에 **파일만** 있으면(스크린샷, 브라우저에서 "이미지 복사", 탐색기에서 파일 복사)
    → 첨부로 올린다. 글은 그대로 둔다.
  - **글과 그림이 같이** 있으면(워드·엑셀·구글 문서에서 복사하면 글 + 그 글을 그린 그림이 함께
    온다) → **글로 붙인다.** 그림까지 올리면 엑셀 몇 칸 복사할 때마다 사진이 한 장씩 올라간다.
    대신 입력칸 아래에 작은 [그림으로 붙이기] 를 잠깐 띄워 원하면 그림으로 바꾼다.
  - 글만 있으면 지금과 같다.
  - 한 번에 여러 파일이 오면 순서대로 모두. 8개를 넘으면 앞의 8개만 받고 알린다.
  - 올라가는 중에도 계속 쓰고 붙일 수 있다. 보내기는 올라가기가 끝나야 켜진다.
- **끌어다 놓기** — 입력칸이 아니라 **대화 화면 전체**가 받는다(작은 칸을 겨냥하게 하지 않는다).
  - 파일을 끌고 들어오면 화면 위에 "여기에 놓으면 첨부돼요" 막이 뜨고, 나가면 사라진다.
    안쪽 요소를 지날 때 깜박이지 않도록 들어오고 나간 횟수를 센다.
  - **파일일 때만** 반응한다. 페이지 안의 글·링크를 끌 때는 막이 뜨지 않는다.
  - 대화 화면 밖에 떨어뜨려도 브라우저가 그 파일을 열어 버리지 않게 막는다(지금은 사진을
    잘못 떨어뜨리면 페이지가 그 사진으로 바뀐다).
  - 폴더는 받지 않는다고 알린다.
- **📎 / 사진**: 휴대폰에서는 사진첩·카메라가 바로 열린다.
- **미리보기 줄**: 이미지는 썸네일, 문서는 아이콘·이름·크기. 올라가는 동안 **실제 진행률**
  (전송 바이트 기준), 실패하면 [다시] · [빼기]. 한 번에 최대 8개. 크기·형식은 **서버가 준 표
  하나**로 미리 거른다(서버와 화면이 따로 표를 들고 있으면 언젠가 어긋난다).
- **키보드**: 📎 는 Tab 으로 닿고, 미리보기 칩은 Delete 로 뺀다. 화면 낭독기에 "사진 2장 첨부됨".
- **말풍선**: 이미지는 격자 썸네일 → 누르면 기존 `PhotoViewer` 로 크게. 문서는 파일 카드
  → 누르면 [파일] 탭의 그 파일.

| 자리 | 지금 → 바뀐 뒤 |
|---|---|
| 비서 대화 | 📎만 → 붙여넣기·끌어다 놓기·미리보기·말풍선 그림 |
| 메신저 | 없음 → 같은 입력. 비서 방은 비서 대화와 같고, 사람끼리 방은 §6-4 |
| 공개 비서 | 없음 → 같은 입력. **기본 켜짐**, 비서 설정에서 끈다 (§6-3) |

### 6-2. [파일] 탭 — 비서 화면 [메모리] 오른쪽

표준 틀(진단·트리거와 같음): 위에 제목, 오른쪽에 보기 전환(격자/목록).

- **거르기 한 줄**: `[기간] [출처: 나와의 대화·방문자·메신저] [종류] [검색]`
- **위 칸 셋**: 파일 수 · 쓴 용량(요금제 한도 대비) · 읽을 수 없는 파일 수
- **격자**: 썸네일(문서는 첫 쪽 또는 아이콘) · 이름 · 날짜 · 출처. 잘린 이름은 공통 호버로 전부.
- **누르면 옆 창**: 미리보기(이미지 크게 / PDF 쪽 / 글 앞부분) · 캡션 · [이 대화로 가기] ·
  [지식으로 올리기] · [공개 범위] · [내려받기] · [지우기]
- 지우면 "비서도 더는 이 파일을 볼 수 없어요" 를 확인받는다.

### 6-3. 공개 비서의 방문자 파일 (결정 2)

- **기본 켜짐.** [비서 설정] → [방문자 설정] 에 **[방문자에게서 파일 받기]** 스위치. plan/53 의
  울타리(하루 전체·시간당 새 대화·분당 말) 바로 옆에 선다.
- 켜져 있을 때의 울타리(같은 화면에서 주인이 바꾼다):
  - 방문자 한 사람이 하루에 올리는 파일 수 — 기본 20
  - 파일 하나의 크기 — 기본 10MB (서버 한도 이하에서만)
- 방문자 파일은 **그 방문자 칸**에 들어간다. 그 방문자와의 대화에서만 비서가 읽고, 다른
  방문자에게는 절대 보이지 않는다. 주인은 [파일] 탭에서 [방문자] 로 걸러 본다.
- 방문자 파일도 주인의 저장 한도를 쓴다. 보존은 그 비서의 방문자 보존 기간(기본 90일).
- 꺼져 있으면 방문자 입력칸에 📎 가 없고, 붙여넣기·끌어다 놓기도 받지 않는다.

### 6-4. 메신저 — 비서는 통로로만, 허락을 받고 (결정 3)

**지금 실측**: 비서가 기록을 읽는 모든 길(대화 기록 `runtime`, 기억 증류 `distill`, 관계 맥락
`relationship`)은 `conversation_id` 로만 찾는다. 사람끼리 방의 말은 `conversation_id` 가 비어
있다(`rooms.say`). 그래서 **지금 비서는 사람끼리 방을 볼 수 없고, 볼 통로도 없다.**

**원칙**: 사람끼리 방은 비서가 **당연히 보는 곳이 아니다.** 비서에게는 통로만 열어 두고, 그
통로는 **주인이 이 방이라고 확인하고 허락한 뒤에만** 열린다. 허락이 나면 그 방의 **모든 자료**
— 양쪽이 한 말과 양쪽이 올린 파일 — 를 볼 수 있다. 주인은 그 방의 참가자라서 이미 전부 볼 수
있는 사람이고, 비서는 주인의 눈을 빌리는 것이다.

비서 방(메신저 창에서 내 비서와 하는 대화)은 비서 대화와 같다 — 여기의 파일은 그 비서의 파일로
자동으로 남는다. 아래는 **사람끼리 방**만의 이야기다.

#### 흐름

```
주인: "수안과의 대화 좀 살펴봐"
  │
  ├─ 비서 ─▶ rooms_find("수안")          ← 방의 겉만: 상대 이름·핸들·마지막 말 시각·말 수·파일 수.
  │                                         내용은 한 글자도 없다.
  │
  ├─ 비서 ─▶ room_access_request(room, 까닭)
  │            └─ 대화에 허락 카드가 뜬다:
  │               ┌──────────────────────────────────────────────┐
  │               │ 최수안(@suan) 님과의 대화를 읽어도 될까요?        │
  │               │ 마지막 말 오늘 10:12 · 말 142개 · 파일 3개        │
  │               │ 까닭: 계약서 이야기를 확인하려고요                │
  │               │ [이번 대화에서만]  [계속 허락]  [아니에요]         │
  │               └──────────────────────────────────────────────┘
  │            (같은 이름이 여럿이면 카드에 후보를 늘어놓고 고르게 한다 — "이게 맞나" 를
  │             묻는 것과 "허락하나" 를 묻는 것을 한 번에)
  │
  ├─ 주인이 누른 것이 곧 다음 턴이 된다 (따로 "허락했어" 라고 쓸 필요 없다)
  │
  └─ 허락되면 ─▶ room_read(room, before?, 개수?, 찾을말?)   ← 양쪽 말 전부 + 첨부 목록(파일 id)
                 file_read / file_view(파일 id)             ← 그 방의 파일도 똑같이 열린다
```

#### 정해 두는 것

| 항목 | 정한 것 |
|---|---|
| 허락의 단위 | **이 비서 × 이 방.** 다른 비서가 같은 방을 보려면 따로 허락받는다 |
| 기간 | [이번 대화에서만] = 그 비서 대화가 끝나면(새 대화를 열면) 닫힌다. [계속 허락] = 거둘 때까지 |
| 거두기 | [내 정보 → 비서가 볼 수 있는 대화] 목록과 메신저 방 정보에서. 거두면 그 순간부터 통로가 닫힌다 |
| 허락 없이 부르면 | `room_read` 는 거절하고 "주인의 허락이 필요해요" 를 돌려준다. 막는 자리는 그 도구 하나 |
| 방문자 대화 | 통로 도구 자체가 없다(주인 대화 전용). 방문자가 "하렴과 수안의 대화" 를 물어도 길이 없다 |
| 기억 | 통로로 읽은 턴은 **기억 증류를 건너뛴다.** 증류가 수안의 말을 사실로 적어 두면, 허락을 거둬도 비서는 계속 알고 있게 된다 — 그건 거둔 것이 아니다. 주인이 "이건 기억해 둬" 라고 하면 그때만 적는다(명시적 기억은 주인의 결정) |
| 파일 | 사람끼리 방의 파일은 어느 비서의 [파일] 에도 자동으로 들어가지 않는다. 허락받은 동안에만 id 로 열린다. 한도는 **올린 사람의 [메신저] 칸** |
| 상대에게 알림 | 하지 않는다. 주인은 그 방을 이미 볼 수 있는 사람이고, 비서는 주인이 허락한 만큼만 본다. 대신 허락·열람은 감사 기록에 남는다 |
| 기록 | 허락 카드와 그 답은 비서 대화에 남는다 — 나중에 "언제 무엇을 허락했나" 를 대화에서 되짚을 수 있다 |

#### 구현

- 표 `room_grants`: `user_id, agent_id, room_id, scope(conversation|always), conversation_id, granted_at,
  revoked_at`. 한 쌍에 살아 있는 허락은 하나.
- 도구 넷(주인 대화 전용): `rooms_find`, `room_access_request`(허락 카드), `room_read`, 그리고 파일
  도구의 `visible_to` 가 **허락된 방의 첨부**를 포함한다. 허락 판정은 `rooms.granted(agent, room,
  conversation)` 한 함수.
- 카드: 기존 카드 틀(`CardRenderer`)에 `room_access` 종류를 더한다. 버튼을 누르면 허락을 기록하고
  그 선택을 사용자 말로 대화에 넣어 턴을 잇는다.
- 턴에 `used_room_read` 표시 → `distill` 이 건너뛴다(심부름 턴 `simulated` 와 같은 자리에서 막는다).
