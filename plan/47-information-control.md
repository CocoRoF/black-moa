# 47. 내 정보가 원장이다 — 정보 공개와 비서 기억 로직 조사

> 이 문서는 **조사 리포트**다. 고친 것은 §7 하나뿐이고, 나머지는 지금 그대로다.
>
> **§8 의 제안은 plan/48 이 대신한다.** 이 문서는 "지금 무엇이 어떻게 돼 있나" 의
> 기록으로 남기고, "어떻게 할 것인가" 는 48 을 본다.

## 0. 지켜야 할 철학

1. **모든 원천은 [내 정보] 아래에서 통제된다.** (+ 커뮤니티에 쓴 글)
2. **비서에게는 기본적으로 모든 정보가 간다.**
3. **[비서] 설정은 그것이 어디까지 나가는지만 정한다.**

곧 **원천은 하나, 공개 범위는 그 위에 얹는 딱지**다. 이 문서는 지금이 그런지 본다.

글**(`kind=blog`), **커뮤니티 실명 글**(`kind=community`).

**②를 지키는 것 다섯, 어기는 것 셋. ①을 지키는 것 넷, 어기는 것 넷.**

## 3. 사실 — 주인의 것인데 비서 밑에 있다

`facts` 행에는 `agent_id` 가 있다. 그런데 **읽을 때 아무도 그것을 보지 않는다.**

```python
# pipeline/runner.py:520 — 주인 것 전부. agent 조건이 없다.
stmt = select(Fact).where(Fact.owner_id == owner_id, Fact.status == "active")
```

제니가 알게 된 사실은 같은 주인의 다른 비서 프롬프트에도 그대로 들어간다. **이것은
맞다.** 철학 ②가 말하는 바다.

틀린 것은 화면이다. 사실은 `/app/agents/{id}/memory` 의 [사실] 칸에 있다. 주소에
비서가 적혀 있으니 "이 비서가 아는 것" 으로 읽힌다. 게다가 목록 API 도:

```python
# api/agents.py:557 — agent_id 를 받고, 소유 확인에만 쓰고, 조회에는 안 쓴다.
await AG.get_owned(db, user.id, agent_id, include_archived=True)
rows = select(Fact).where(Fact.owner_id == user.id, ...)
```

**비서가 셋이면 같은 목록이 세 군데 있고, 어디서 지워도 셋 다에서 사라진다.**
지운 사람은 한 비서에서만 지웠다고 생각한다. 이건 표시가 거짓말을 하는 것이다.

한 가지 더 어긋난다. 사이(관계) 화면이 세는 사실 수는 **비서별로** 센다.

```python
# services/relationship.py:173 — 이쪽은 agent 를 본다.
(Fact.agent_id == agent_id) | (Fact.agent_id.is_(None))
```

읽을 때는 주인 단위, 셀 때는 비서 단위다. 같은 표를 두 규칙으로 본다.

**고칠 방향.** 사실은 `[내 정보] › 사실` 로 옮긴다. 목록에서 "누가 알게 됐는지" 는
행의 꼬리표로 남기되, 그것이 범위를 가르지는 않는다. 관계가 세는 수도 주인 단위로
맞춘다(아니면 "이 비서가 알게 된 사실" 이라고 이름을 바꾼다).

## 4. 프로필 — 같은 질문에 답하는 곳이 둘

```python
# services/profile.py:157
normalize_visibility((profile.visibility or {}).get(field)        # ① 내 정보
                     or pf.get(field)                              # ② 비서의 disclosure_policy
                     or DEFAULT_FIELD_VIS.get(field) or "private")
```

`내 정보` 에서 정하면 그것이 이긴다. 안 정했으면 **비서 설정이 정한다.**

철학 ③으로 보면 "공개 범위는 비서 설정" 이니 ②가 있는 것 자체는 맞다. 문제는
**둘 다 있고 우선순위로 가려진다**는 것이다. 화면 둘이 같은 칸에 서로 다른 값을
보여 줄 수 있고, 어느 쪽이 실제인지는 코드를 읽어야 안다.

게다가 기본값이 셋이다. 내 정보에 없고, 비서 정책에도 없으면 `DEFAULT_FIELD_VIS`.
그리고 `DEFAULT_DISCLOSURE.profile_fields` 는 **또 다른 기본값**이다. `location` 이
한쪽은 `public`, 다른 쪽은 `private` 이다.

> **정정 (2026-09-22).** 위 문단에서 `location` 의 기본값이 두 표에서 다르다고 적었는데
> **틀렸다.** `DEFAULT_FIELD_VIS` 에는 `location` 이 아예 없어서 `private` 으로 떨어지고,
> `DEFAULT_DISCLOSURE` 도 `private` 이다. 두 표를 칸마다 맞춰 보니 **한 칸도 다르지
> 않았다.** 그래서 비서 정책을 걷어내는 것은 기본값에 관한 한 동작이 바뀌지 않는다
> (운영에서 직접 손댄 한 건도 [내 정보] 에 같은 값이 있어 바뀐 것이 없었다).
> 문제는 값이 다른 것이 아니라 **같은 질문에 답하는 곳이 둘이라는 것**이었다.

**고칠 방향.** 칸의 공개 범위는 `owner_profiles.visibility` 하나로 한다. 비서 정책의
`profile_fields` 는 지우고, 그 자리에는 "이 비서에게는 더 좁게" 같은 **덮어쓰기만**
남기거나 아예 없앤다. 기본값 표는 하나만 남긴다.

## 5. 지식 — 철학 ②를 어기는 유일한 원천

```python
# pipeline/runner.py:500
if (agent.capabilities or {}).get("knowledge", True):
    hits = await K.search(...)
```

비서 설정에서 [지식] 능력을 끄면 **그 비서는 지식 문서를 아예 못 본다.** 이건
"어디까지 나가나" 가 아니라 "비서가 아느냐" 를 비서 설정에서 정하는 것이라 ②와 ③
둘 다에 어긋난다.

검색 층은 오히려 맞다.

```python
# services/knowledge.py:193 — 주인이 물으면 범위를 안 따진다.
vis_clause = "" if audience == "owner" else " AND d.visibility = 'public'"
```

주인의 턴은 `private` 문서도 찾고, 방문자의 턴은 `public` 만 찾는다. 딱지 하나로
두 세계가 갈린다. **이것이 이 서비스에서 가장 잘된 부분이다.**

문서가 비서에 묶일 수도 있다(`d.agent_id`). 이건 "이 비서만 쓰는 자료" 라는 뜻이라
원천을 나누는 것이지 공개 범위가 아니다. 남겨도 되지만, 그렇다면 **[내 정보] › 지식**
에서 그 묶음까지 보여야 한다. 지금은 비서별 지식이 `/app/agents/{id}/knowledge` 에
따로 있어서, 내 지식이 몇 개인지 한 화면에서 셀 수 없다.

## 6. 원천을 통째로 끊는 스위치 둘

- **인맥**: `users.network_to_secretary`. 끄면 인맥 요약도 도구도 전부 사라진다
  (`runtime.py:159`, `tools/base.py:84`). 화면은 `/app/network` 안이라 자리는 맞다.
- **구글**: `/app/integrations`. **왼쪽 줄 어디에도 없다.** 내 메일과 일정이 비서에게
  가는데, 그 스위치로 가는 길이 메뉴에 없다.

둘 다 ②("비서에게는 전부 간다")를 주인이 스스로 끄는 것이라 철학 위반은 아니다.
다만 **원천을 끄는 스위치는 전부 [내 정보] 아래 한자리에 모여야** 주인이 "내 무엇이
비서에게 가고 있나" 를 한 화면에서 답할 수 있다.

## 7. 프로필 배치 (이번에 고쳐 배포함)

개인 프로필의 오른쪽 칸을 **정보 → 공개 비서 → 링크** 로 세웠다.

- 누구나 말을 걸 수 있는 비서(공개 링크가 살아 있는 것)만 선다. 링크가 없는 비서는
  **없는 것처럼** 다룬다. 이름만 보여 주고 못 누르게 두면 "있는데 막혔다" 로 읽혀
  문을 닫아 둔 사람의 뜻과 어긋난다.
- 내 페이지에서도 같은 카드가 보인다. **남에게 어떻게 보이는지를 내가 볼 수 있어야**
  공개 설정이 손에 잡힌다. "열어 둔 비서가 없다" 는 말은 내 페이지에서만 한다.
- 자료는 이미 `profile_of` 가 주고 있었고(`out["secretaries"]`), 화면만 없었다.

## 8. 정리 — 무엇을 고쳐야 하나

우선순위 순이다.

1. **사실을 [내 정보] 아래로.** 지금은 주인의 것을 비서 밑에 두어 화면이 거짓말을
   한다. 읽기·세기 규칙도 한쪽으로 맞춘다. (§3)
2. **[지식] 능력 스위치를 없앤다.** 비서가 내 지식을 아느냐는 비서 설정이 정할 일이
   아니다. 끄고 싶으면 문서를 지우거나 범위를 좁힌다. (§5)
3. **프로필 칸의 공개 범위를 한 군데로.** `owner_profiles.visibility` 를 정본으로
   삼고 기본값 표도 하나만 남긴다. (§4)
4. **원천 스위치를 한자리에.** 구글 연동을 [내 정보] 아래로 올리고, 인맥·구글·지식을
   "내 무엇이 비서에게 가나" 한 화면에서 보이게 한다. (§6)
5. **비서별 지식도 [내 정보] › 지식에서 보이게.** 묶음은 나뉘어도 목록은 하나다. (§5)

### 안 고쳐도 되는 것

- **주인 턴은 전부 보고 방문자 턴은 공개만 본다** 는 한 줄 규칙(`knowledge.py:193`).
  이 규칙이 철학 ②·③을 정확히 구현한 유일한 자리이고, 나머지를 여기에 맞추면 된다.
- **필명 글은 비서에게 가지 않는다**(plan/41 §1, plan/45 §10). 이것은 공개 범위가
  아니라 경계이고, 지금 코드가 지키고 있다.
