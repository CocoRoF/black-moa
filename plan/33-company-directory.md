# 기업정보 — 국가·공개 API에서 모아 커뮤니티에 붙이기

> **상태 (2026-09-11): 1~5단계 구현·배포 완료. 6단계(국민연금)만 남음.**
> 키 없이 동작하는 부분은 프로드에서 실증됐고, 키가 필요한 부분은 **키를 넣는 순간
> 동작하도록 배선까지 끝났다**(관리자 화면에서 키 입력 → [수집]).
>
> - **실측**: KRX 수집 3.7초 / 2,802행 → **2,759개사**(코스닥 1819·유가 832·코넥스 108),
>   업종코드 99.6%·지역코드 99.9%. 커뮤니티 `업종=IT·지역=서울` → 188개사.
> - **키 없이 돌린 3개 출처**는 `needs_key` 로 기록되고 워커는 죽지 않는다(로그 info,
>   `job done`). 관리자 화면이 **어느 설정이 비었는지 + 어디서 받는지**를 말한다.
> - **자동 수집**: `companies.refresh` 를 하루 1회 스케줄. 출처별로 **각각 잡을 큐에 넣어**
>   하나가 느리거나 한도에 걸려도 나머지가 멈추지 않는다. 기본 꺼짐.
> - **실측으로만 나온 데이터 문제 5건**은 §8 에 적었다.

> 목표: 커뮤니티(특히 채용 공고)에서 **실제 기업정보**를 보여준다. 수단은 사용자 요청 때
> 남의 서버를 찌르는 것이 아니라, **워커의 배치 수집 + 우리 DB**다.

## 0. 어디서 가져오나 — 실제로 찔러보고 확인한 것

전부 오늘(2026-09-11) 이 저장소에서 직접 호출해 확인했다. "있다더라"가 아니다.

| 출처 | 키 | 실측 | 주는 것 |
|---|---|---|---|
| **KRX 상장법인목록** `kind.krx.co.kr/corpgeneral/corpList.do?method=download` | **불필요** | **200, 1.26MB, 2,802개사** | 회사명·시장구분(유가/코스닥/코넥스)·종목코드·업종·주요제품·상장일·결산월·대표자명·홈페이지·지역 |
| **DART OpenAPI** `opendart.fss.or.kr` | 필요 (무료·즉시발급, 20,000회/일) | `{"status":"010","message":"등록되지 않은 인증키입니다."}` — 계약 확인됨 | `corpCode.xml`=전체 공시대상 법인(비상장 포함) 목록 + 종목코드↔corp_code, `company.json`=사업자등록번호·법인등록번호·주소·전화·설립일·업종코드·대표자 |
| **국세청 사업자등록정보 상태조회** `api.odcloud.kr/api/nts-businessman/v1/status` | 필요 (data.go.kr, 무료) | `{"code":-4,"msg":"등록되지 않은 인증키 입니다."}` — 계약 확인됨 | 사업자등록번호 → 계속사업자/휴업자/**폐업자**, 과세유형 |
| 국민연금 가입사업장 (data.go.kr) | 필요 | 미확인 | 사업장별 가입자 수 = 사실상 유일한 무료 **인원 규모** 신호 |

**KRX 하나로 키 없이 즉시 동작한다**는 점이 중요하다. 키를 받아 넣기 전에도 2,802개사가
채워지고, 키는 *보강*일 뿐 전제가 아니다. 비상장까지 넓히려면 DART 키가 필요하다.

한국기업데이터·NICE평가정보는 유료라 제외한다.

## 1. 왜 배치인가

세 가지 모두가 같은 결론을 가리킨다.

1. **한도.** DART 20,000회/일. 상장사 전체 보강이 한 번에 2,802회다. 사용자 요청마다
   호출하면 한도는 하루도 못 간다.
2. **변하지 않는다.** 상장법인 목록은 하루 단위로 바뀌고, 사업자등록 상태는 그보다 느리다.
   요청 시점에 새로 물어볼 이유가 없다.
3. **남의 서버를 우리 지연에 넣지 않는다.** 커뮤니티 목록 쿼리는 15초 예산이다(plan/32 §5).
   KRX가 느린 날 우리 게시판이 느려지는 구조는 만들지 않는다.

그래서 `crawl` 클래스로 들어간다 — plan/32 §4에서 **바로 이것을 위해** 비워 둔 자리다
(슬롯 상한 3, 전용 스레드 풀 `crawl` 12, `crawl.*` 접두사로 집계·제외).

## 2. 스키마

한 회사 = 한 행. 출처가 여러 개이므로 **어느 출처가 무엇을 채웠는지**를 같이 남긴다.

```
companies
  id
  name            표시명 (KRX 회사명 → DART 정식명으로 승격)
  name_norm       매칭용 정규화 (공백·(주)·주식회사 제거)
  stock_code      상장사만. KRX·DART 조인 키
  corp_code       DART 고유번호. DART 조인 키
  biz_no          사업자등록번호. 국세청 조인 키 (알게 되면)
  market          유가 | 코스닥 | 코넥스 | (비상장)
  industry_text   출처 원문 ("의료용 기기 제조업")
  industry_codes  우리 분류 코드로 매핑한 것 (JSONB)
  region_code     시도 코드. KRX 지역 라벨이 data/regions 라벨과 정확히 일치한다
  ceo, homepage, product, listed_on, fiscal_month
  address, phone, founded_on, employees        ← DART/연금 보강분
  status          active | closed | unknown     ← 국세청
  sources         {"krx": "2026-09-11T…", "dart": …}  어느 출처가 언제 손댔는지
  updated_at
```

`community_jobs.company_id` (nullable FK) 를 추가한다. 공고의 `company` 문자열은 남겨
둔다 — 매칭이 안 되는 회사도 공고는 올라가야 한다.

## 3. 수집기

출처당 한 모듈, 전부 같은 모양(`fetch() -> list[dict]`, `merge()`):

- `krx.py` — HTTP 1회. **EUC-KR HTML 표**를 Excel 이라고 주므로 그대로 파싱한다.
- `dart_codes.py` — `corpCode.xml` (zip) 1회 → 종목코드↔corp_code 사전.
- `dart_company.py` — corp_code 당 1회. 한도 안에서 **가장 오래된 것부터** 나눠 돌린다.
- `nts_status.py` — 사업자번호 100개씩 묶어 상태 확인.

**병합 규칙**: 출처마다 신뢰하는 필드가 다르다. 사업자번호·주소·설립일은 DART, 상태는
국세청, 종목코드·시장·주요제품은 KRX 가 이긴다. 사람이 고친 값은 아무 출처도 못 덮는다.

## 4. 관리자

[커뮤니티] 옆 [기업정보] 섹션:
- 출처 표 — 키 등록 여부, 마지막 수집 시각, 가져온 행 수, 실패 사유
- [수집 시작] 버튼 → 잡을 큐에 넣는다(즉시 실행이 아니라 큐, 이유는 §1)
- 기업 검색 표 — 이름·종목코드·업종·지역, 행 클릭 시 출처별 값
- 키 입력은 기존 관리자 시크릿 필드 패턴을 그대로 쓴다(마스킹·부분 저장)

## 5. 커뮤니티 표면

- 채용 공고에 **기업정보 카드** — 업종·지역·대표자·홈페이지·상장시장, 폐업이면 경고
- `/community/companies` 디렉터리 — 업종·지역 필터(이미 있는 분류 체계 재사용)
- 공고 작성 시 회사명 자동완성 → `company_id` 연결

## 6. 단계

| 단계 | 내용 | 키 필요 |
|---|---|---|
| 1 | 스키마 + KRX 수집기 + `crawl.companies.krx` 핸들러 + 관리자 출처 표 | **불필요** |
| 2 | 관리자 기업 검색·상세, 커뮤니티 디렉터리 | 불필요 |

## 7. 하지 않는 것

- **스크래핑하지 않는다.** 잡코리아·사람인 같은 곳을 긁는 것은 약관 문제이고 깨지기 쉽다.
  국가·거래소가 주는 것만 쓴다.
- **유료 DB 안 쓴다.**
- **요청 시점 조회 안 한다** (§1).
- 사람이 고친 값을 배치가 덮지 않는다.


## 8. 실측으로만 드러난 것들 (구현 중 발견)

계획서로는 나올 수 없었던 것들이다. 전부 실제 응답을 받아 본 뒤에 알았다.

1. **KRX 가 43개사를 두 번 싣는다.** 2,802행인데 고유 종목코드는 2,759. 두 행의 차이는
   `지역` 한 필드뿐이고, 행정구역 개편 중이라 `전남광주통합특별시` / `전라남도` 처럼 한쪽만
   코드로 해석된다 → **지역은 code+text 쌍으로 움직여야** 한다. 필드별로 쓰면 코드는 A행,
   라벨은 B행이 남아 서로 어긋난다.
2. **해외 설립 상장사 22곳**(홍콩·미국·케이맨·싱가포르·영국·일본)은 지역이 국가명이다 →
   분류체계에 이미 있던 `99`(해외·원격)로. 안 하면 지역 필터에 영원히 안 걸린다.
3. **업종 매핑 89.6% → 99%**: 미스의 대부분이 **띄어쓰기**였다("정보 서비스업" vs
   "정보서비스"). 공백 무시 매칭 + 누락 카테고리(선박·시멘트·종이·사료·케이블·화물운송).
4. **맨 키워드 `시험` 이 "측정, 시험, 항해, 제어 및 기타 정밀기기 제조업" 을 잡아** 계측기
   제조사를 `public.research` 로 보냈다. 화면 스크린샷에서 발견. 커버리지 숫자가 99.6%→98.9%
   로 내려갔는데, 그 차이가 곧 **잘못 분류된 회사 수**였다.
5. **`CommunityJob(...)` 는 필드를 명시 열거한다** → 매칭이 구해 준 `company_id` 가 조용히
   버려졌다. 호출이 아니라 **결과를 단정하는 테스트**만이 잡을 수 있었다.

## 9. 다음에 키를 넣으면 할 일

DART 키를 넣은 뒤 `dart_codes` → `dart` 순서로 돌린다(고유번호를 먼저 알아야 기업개요를
부를 수 있다). `companies.dart_per_run`(기본 1500)이 하루 한도 20,000 안에서 나눠 돌게
하고, 오래된 것부터 이어서 돈다. 그 다음 `nts` 로 폐업을 표시한다.

## 10. 재시작에 견디는 수집 (2026-09-14)

이틀치 수집 로그가 전부 `dart … 중단됨 — 워커가 재시작되었어요`(조회 0)였다. 실측으로 잡은 원인 셋과 대책:

1. **DART 가 준 자리표시 사업자번호**("11940" 같은 5자리)를 잘라 저장해 여러 회사가 같은 키를 갖게 됐고,
   UNIQUE 위반이 첫 묶음에서 터졌다. 게다가 예외 뒤 같은 세션으로 기록을 닫으려다(롤백 상태) 실패해 행이
   `finished_at IS NULL` 로 남아 "수집 중…" 이 됐다. → 10자리가 아니면 버림(`parse_company`), 병합이 다른 회사가
   쥔 고유키(corp_code/biz_no/stock_code)는 쓰지 않고 넘어감(`_held_elsewhere`), 묶음마다 savepoint.
2. **취소(잡 900초 타임아웃·워커 종료)는 `except Exception` 에 안 잡혀** 기록이 열린 채 남았다. → 기록의 종료는
   **별도 세션**(`_close_record`)으로 항상 쓰고, `CancelledError` 도 닫은 뒤 그대로 올린다.
3. **스케줄러 시계가 메모리**라 워커가 뜰 때마다 "24시간마다" 가 즉시 발화 → 배포마다 전 출처 수집이 시작돼
   다음 배포에 죽었다. → `_seed_schedule` 이 jobs 의 마지막 생성 시각으로 시계를 채우고, `companies.refresh` 는
   20시간 안에 성공한 출처를 건너뛴다(`ran_recently`, `{"force": true}` 로 강제).

그리고 **긴 잡을 없앴다**: dart 는 호출마다 시계를 보고 600초에 멈추며, 남은 회사와 한도가 있으면 **자기 후속
잡을 큐에 넣는다**(`companies:dart:continue:<run_id>` 로 중복 방지). 하루치 1만 건은 짧은 잡 서너 개의 사슬이
되고, 재시작이 잃는 것은 진행 중이던 묶음 하나뿐이다. 조회 수는 병합 전에 기록해 한도 계산이 어긋나지 않는다.
nts 는 묶음마다 3회 재시도·묶음 단위 반영.
